# 부하 측정 결과

6단계(DESIGN 6.6)의 숫자입니다. 모두 같은 PC(i5-13600K, 64GB)에서 잰 전후 비교이고 절대 처리량을 주장하지 않습니다. 원본은 `load/results/runs/`(gitignore)에 있습니다.

조건:
- API는 P코어 0~11, k6는 E코어 12~19에 묶습니다. PostgreSQL 18.6은 기본 설정입니다(`shared_buffers` 128MB, `max_connections` 100).
- 로그는 warn이고, 부하 DB는 템플릿에서 복제합니다(autovacuum 끔).
- 이 PC는 쉴 때도 다른 프로세스가 CPU를 1.5~2.5코어쯤 씁니다(회차마다 k6 전 5초를 잼).
- 백분위는 k6가 잰 것입니다(클라이언트 쪽). 서버 처리 시간은 API의 1초 줄에서 봅니다.

- 풀 5의 지연이 가장 짧습니다. 동시에 연 트랜잭션이 적으면, 밀린 이벤트 루프가 하나씩 끝내는 것이 빠른 것으로 봅니다. 탐색 회차라 한 번씩이므로 확인 회차(풀 5와 10, 다섯 번씩 번갈아)에서 다시 봅니다.

### 표 통계에서 본 것

- **좌석 지도**: 요청마다 `performances`(200행)와 `seats`(2,000행)를 순차 탐색합니다. 둘 다 작고 그 요청이 읽어야 하는 전부라 병목이 아닙니다. 재고(`performance_seats`)는 기본 키로 찾습니다.
- **S3**: 큰 표의 순차 탐색은 없습니다. `idempotency_keys`와 `payment_webhooks`의 순차 탐색 수십 번은 정리 작업입니다.
  - 부하 DB는 autovacuum을 꺼 두어 통계가 템플릿을 만들 때(빈 표)에 머뭅니다. 그래서 계획기가 인덱스 대신 순차 탐색을 고릅니다.
  - 측정 조건에서 생긴 것이고 수가 작습니다(10분에 67번).
- **인덱스가 없는 외래 키 열, 겹치는 인덱스**: 이 부하에서 비용이 보이지 않았습니다(부모 행을 지우는 흐름이 없음).
- **`holds(performance_id)`**: 관리자 판매 현황 질의가 쓰는데, 부하 시나리오에 관리자가 없어 재지 않았습니다.

## 개선 1: 좌석 지도 JSON을 PostgreSQL이 만든다

기준선 프로파일에서 Node 시간 대부분이 2,000행을 객체로 받아(pg 파싱·Drizzle 매핑) 다시 검증·직렬화하는 데 들었습니다. 그래서 회차 요약과 좌석을 한 문장에서 만들고, Node는 그 글자를 그대로 보냅니다.
- 사용한 함수는 `json_build_object`, `json_agg`, `row_to_json`입니다.
- 응답 모양은 같습니다. 행으로 만들던 구현과 같은지 보는 테스트를 두었고, `SeatMap` 검증도 합니다.
- 값과 키 순서는 같고 바이트는 약 3% 늘었습니다. PostgreSQL이 원소 사이와 키 뒤에 빈칸을 넣습니다(2,000석이면 약 6KB).
- 질의는 두 번에서 한 번이 됩니다.

- 이 프로젝트처럼 API 하나와 DB 하나가 한 PC에 있으면 맞는 거래입니다. Node는 한 스레드라 먼저 차고, postgres는 연결마다 다른 코어를 씁니다.
- API를 여러 대로 늘리고 DB 하나를 나눠 쓰는 구성이라면 DB CPU가 먼저 귀해집니다. 그때는 DB 일을 늘리지 않는 방법이 맞습니다.
  - 프로파일에서 Drizzle 매핑, zod 응답 검증, JSON 직렬화가 Node 일한 시간의 약 43%였습니다.
  - 행을 배열로 받아(`rowMode: 'array'`) 직접 JSON 글자를 만들면 DB 일을 늘리지 않고 그만큼을 덜 수 있습니다(재지 않음).
