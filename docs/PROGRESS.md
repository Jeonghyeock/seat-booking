### 0단계 — 설명할 수 있어야 할 것

**마이그레이션은 어떻게 적용되고, 어떻게 되돌리나**

1. `npm run db:generate`(drizzle-kit generate)는 `src/db/schema.ts`를 직전 스냅샷(`drizzle/meta/*_snapshot.json`)과 비교해 바뀐 부분만 SQL 파일(`drizzle/0000_init.sql`)로 쓴다. `drizzle/meta/_journal.json`에는 파일마다 만든 시각(`when`)이 남는다.
2. `npm run db:migrate`(`src/db/migrate.ts`)는 DB의 `drizzle.__drizzle_migrations` 표에서 마지막으로 적용한 마이그레이션의 시각(실행 시각이 아니라 그 파일을 만든 시각, journal의 `when`)을 읽는다. 그보다 나중에 만든 파일만 차례로 실행하고, 실행한 파일마다 SQL의 해시와 그 파일을 만든 시각을 그 표에 적는다.
3. 아직 적용하지 않은 파일은 **트랜잭션 하나 안에서** 모두 실행한다. PostgreSQL은 `CREATE TABLE` 같은 DDL도 트랜잭션으로 되돌릴 수 있으므로, 중간에 하나가 실패하면 그 실행의 변경은 전부 취소된다. 트랜잭션 안에서 실행할 수 없는 문장(`CREATE INDEX CONCURRENTLY` 등)은 이 마이그레이터로는 실행할 수 없다("cannot run inside a transaction block" 오류). 7단계에서 마이그레이터 밖에서 돌린다.
4. 주의할 점이 두 가지 있다.
   - 이미 적용한 파일을 고쳐도 다시 실행되지 않는다. 해시를 적어 두기만 하고 비교하지는 않는다.
   - 다른 브랜치에서 더 이른 시각에 만든 파일이 늦게 합쳐지면, 마지막 시각보다 앞서므로 건너뛴다. 그래서 마이그레이션은 main에 들어간 순서대로 만들어야 한다.
5. Drizzle에는 되돌리는(down) 마이그레이션이 없다. 운영에서 되돌리려면 반대 동작을 하는 마이그레이션을 새로 만들어 앞으로 적용한다. 개발 DB는 지우고 처음부터 다시 적용하면 된다. 테스트 DB는 실행마다 새로 만든다.

**연결 풀은 왜 쓰나**

1. PostgreSQL은 연결 하나마다 서버 프로세스를 하나 띄운다. 연결을 맺을 때마다 TCP 연결, 인증(SCRAM), 프로세스 생성이 일어나므로 요청마다 새로 연결하면 느리고, 서버 메모리도 연결 수만큼 쓴다.
2. `pg.Pool`은 연결을 필요할 때 맺고, 다 쓴 연결은 닫지 않고 남겨 두었다가 다시 쓴다. 기본값은 최대 10개, 10초 동안 쓰지 않은 연결은 닫는다. 연결이 모두 쓰이고 있으면 다음 요청은 빌 때까지 기다린다. 그래서 DB가 받는 연결 수(기본 `max_connections` 100)를 앱 쪽에서 넘지 않게 막는 역할도 한다.
3. 이 저장소에서는 `main.ts`가 풀 하나를 만들어 앱 전체가 쓰고, 서버를 닫을 때 풀도 닫는다. `pool.query()`는 쿼리 하나마다 연결을 빌렸다가 바로 돌려준다.
4. 2단계부터 중요해지는 점: 트랜잭션은 같은 연결에서 `BEGIN`부터 `COMMIT`까지 이어져야 한다. `pool.query()`를 여러 번 부르면 서로 다른 연결로 갈 수 있으므로, 트랜잭션은 `pool.connect()`로 연결 하나를 빌려 그 안에서 처리하고 끝나면 돌려준다.

### 1단계 — 설명할 수 있어야 할 것

**정규화를 어디까지 했나**

기준은 "한 가지 사실은 한 곳에만 둔다"이다. 같은 사실이 여러 행에 있으면, 고칠 때 일부만 바뀌어 서로 어긋날 수 있다.

1. 나눈 것
   - 좌석 배치(구역·열·번호·등급)는 공연장의 사실이라 `seats`에 한 번만 둔다. 회차마다 달라지는 것은 판매 상태뿐이라 `performance_seats`에는 상태만 둔다.
   - 작품 제목은 회차가 아니라 작품의 사실이라 `shows`로 뺐다. 회차에 두면 제목이 회차 수만큼 되풀이되고, 제목을 고칠 때 일부 회차만 바뀔 수 있다.
   - 가격은 (회차, 등급)으로 정해진다. 좌석 재고 행에 두면 회차 하나에 같은 값이 수십 번 되풀이되고, VIP 가격을 바꾸려면 VIP 좌석 행을 전부 고쳐야 한다. 그래서 `performance_grades`로 뺐다.
2. 일부러 나누지 않은 것
   - 등급 표는 따로 없다. `seats.grade`와 `performance_grades.grade`는 둘 다 글자이고 외래 키가 없어서, 오타 난 등급도 들어간다. 등급 표를 두더라도 "좌석의 등급마다 그 회차의 가격 행이 있다"는 외래 키로 지킬 수 없어서, 가격 행은 빠질 수 있다. 그래서 시드는 넣기 전에 이를 확인하고, 좌석 지도는 그런 좌석도 `price: null`로 보여 준다. 관리자가 회차를 등록하게 되면(4단계) 같은 확인을 API에도 둔다.
   - 구역과 열도 표로 빼지 않았다. 좌석 지도를 그리는 데만 쓰고, 따로 바뀌지 않는다.
   - 등급은 좌석에 고정했다. 같은 좌석의 등급이 회차마다 달라야 한다면(어떤 회차는 2층 전체를 R석으로 파는 경우) 등급을 `performance_seats`로 옮겨야 한다. 지금은 그런 요구가 없다.
3. 일부러 미리 만들어 두는 것
   - `performance_seats`는 회차를 만들 때 공연장 좌석 수만큼 행을 채운다. "행이 없으면 빈 좌석"으로 두고 선점할 때 행을 넣는 방법도 있다. 미리 채운 이유는 좌석 지도가 재고 표 하나만 읽으면 되고, 선점·만료·판매를 한 행의 상태 변화로 다룰 수 있어서다. 2단계의 조건부 UPDATE도 이 행을 대상으로 한다.
   - 3단계의 `orders.amount`에는 주문할 때의 가격을 복사하기로 했다. 가격을 되풀이하는 것처럼 보이지만, "그때 낸 금액"은 지금 가격과 다른 사실이다.

**이 조회에 어떤 인덱스가 쓰이나**

임시 DB에 샘플 시드와 회차 300개를 넣었다(회차 303개, 재고 29,694행). 좌석 지도 조회의 `EXPLAIN (ANALYZE, BUFFERS)`를 두 번 돌려 두 번째 결과를 봤다. 아래 3의 표에서 `seats`가 20,098행인 두 경우는, 다른 공연장 200곳의 좌석 20,000개를 샘플 시드 뒤에 넣거나(이 공연장 좌석 id가 앞) 앞에 넣었다(뒤).

실행 시간은 세 경우 모두 0.1ms 안팎이라 시간으로는 차이를 말할 수 없어서 Buffers로 본다. Buffers는 쿼리가 페이지를 건드린 횟수다. 같은 페이지를 다시 건드려도 매번 센다. 두 번째 실행이라 모두 메모리(shared buffers)에 있었고, 디스크에서 읽은 것은 없다.

1. `performance_seats`: 기본 키 `(performance_id, seat_id)`의 Index Scan(`Index Cond: performance_id = 1`). 기본 키의 맨 앞 열이 `performance_id`라 한 회차의 재고는 인덱스 안에서 한 구간에 모여 있다. 29,694행 중 98행을 Buffers 3으로 찾는다.
2. `performance_grades`: 조인 조건(`performance_grades.performance_id = performance_seats.performance_id`)과 `WHERE performance_seats.performance_id = 1`에서 PostgreSQL이 `performance_grades.performance_id = 1`을 이끌어 낸다. 그래서 기본 키 `(performance_id, grade)`로 이 회차의 등급 3행만 읽는다(Bitmap Index Scan).
3. `seats`: 데이터에 따라 읽는 방법이 바뀐다.

   | `seats` 행 수 | 이 공연장 좌석 id의 위치 | 읽는 방법 | 쿼리 전체 Buffers |
   |---|---|---|---|
   | 98(1페이지) | — | 표 전체(Seq Scan) + Hash Join, 마지막에 좌석 id로 정렬 | 7 |
   | 20,098 | 앞(1~98) | `seats_pkey` Index Scan + Merge Join. 양쪽이 이미 좌석 id 순서라 정렬이 없다 | 9 |
   | 20,098 | 뒤 | 좌석마다 `seats_pkey`로 한 번씩 찾는다(Nested Loop, 98번). 좌석마다 인덱스 두 페이지와 표 한 페이지를 건드린다 | 300 |

   표가 1페이지면 통째로 읽는 편이 싸다. 좌석 id가 앞에 있으면 두 인덱스를 좌석 id 순서로 나란히 읽는다(Merge Join). 뒤에 있으면 Merge Join은 `seats_pkey`를 처음부터 읽어야 하고, Hash Join은 `seats` 2만 행을 모두 읽어야 한다. 그래서 98석을 하나씩 찾는 쪽의 비용 추정이 가장 낮다. 플래너는 Buffers가 아니라 비용 추정으로 고르므로, Buffers가 가장 적은 계획을 고른다는 보장은 없다.
4. 실행 계획 테스트(`seat-map-plan.test.ts`)는 `performance_seats` 기본 키가 쓰이는지만 확인한다. `seats`를 읽는 방법은 데이터에 따라 바뀌므로 테스트로 고정하지 않는다.
5. 만들지 않은 인덱스: PostgreSQL은 외래 키 열에 인덱스를 자동으로 만들지 않는다. `performance_seats.seat_id`, `performances.show_id`·`venue_id`에는 인덱스가 없다. 이 열들의 인덱스는 참조되는 행(좌석·작품·공연장)을 지우거나 그 열로 찾을 때 필요하다. 지금은 둘 다 하지 않는다. `seat_id`는 기본 키의 두 번째 열이라, `seat_id`만으로 찾을 때는 기본 키 인덱스를 잘 쓰지 못한다(PostgreSQL 18의 skip scan은 회차 수가 적을 때만 도움이 된다). `seats.venue_id`는 맨 앞 열이 `venue_id`인 unique 제약의 인덱스가 대신한다. 회차 목록은 `starts_at`으로 정렬하지만 인덱스가 없다. 회차가 많아져 목록에 페이지를 붙일 때 다시 본다.

### 2단계 — 설명할 수 있어야 할 것

**조건부 UPDATE가 왜 안전한가**

1. 확인과 수정이 한 문장이다. ① 조회 후 수정은 `SELECT`로 확인하고 `UPDATE`로 고치는 두 문장이라, 그 사이에 다른 요청이 같은 좌석을 읽고 고칠 수 있다. 테스트에서 두 요청이 모두 성공하고, 좌석에는 나중에 쓴 선점만 남았다.
2. `UPDATE`는 고치는 행에 쓰기 잠금을 잡는다. 같은 행을 고치려는 다른 트랜잭션은 앞 트랜잭션이 커밋하거나 되돌릴 때까지 기다린다.
3. 기다리던 쪽은 앞 트랜잭션이 커밋하면, 그 행의 새 버전으로 `WHERE`를 다시 본다. 좌석이 이미 `held`면 조건이 거짓이라 0행을 받는다. 그래서 "빈 좌석이면 바꾼다"는 한 번만 참이 된다.
4. 여러 좌석은 한 트랜잭션에서 잡고, 바뀐 행 수가 담은 수보다 적으면 트랜잭션을 되돌린다. 그때 넣은 선점 행도 함께 사라진다.

**READ COMMITTED에서 겹친 UPDATE는 어떻게 되나**

1. READ COMMITTED에서는 문장마다 스냅샷을 새로 잡는다. `UPDATE`는 문장을 시작할 때의 스냅샷으로 고칠 행을 찾는다.
2. 찾은 행을 다른 트랜잭션이 고치는 중이면 기다린다. 그 트랜잭션이 되돌리면 원래 행으로 진행한다. 커밋하면 행의 새 버전에 `WHERE`를 다시 평가해, 맞으면 고치고 아니면 건너뛴다. PostgreSQL 코드에서는 EvalPlanQual이라고 부른다.
3. 다시 볼 때 새 값으로 보는 것은 고치려는 그 행뿐이다. 조건 안에서 다른 표를 보는 부분(서브쿼리)은 여전히 문장을 시작할 때의 스냅샷으로 본다. 그래서 만료를 `holds`에서 보는 조건("유효한 선점이 없으면")은 앞 트랜잭션이 막 넣은 선점 행을 보지 못해 두 요청이 모두 선점했다(테스트). 만료 시각을 좌석 재고 행에도 둔 이유다.
4. `now()`는 트랜잭션을 시작한 시각이다. 잠금(advisory lock, 좌석)을 오래 기다리는 사이 만료된 선점은 아직 유효해 보여 HOLD_LIMIT이나 409가 날 수 있다. 틀려도 좌석을 더 주는 쪽은 아니다.
5. 여러 행을 서로 다른 순서로 잠그면, 각자 하나를 쥐고 상대 것을 기다리는 교착이 된다. PostgreSQL은 `deadlock_timeout`(기본 1초) 뒤 기다림의 고리를 찾아 한쪽을 40P01로 실패시킨다(테스트). 모든 요청이 좌석 id 순서로 잠그면 고리가 생기지 않는다.
6. 그 순서는 실행 계획에 맡기면 안 된다. 기본 키 인덱스로 읽으면 좌석 id 순서지만, 표를 처음부터 읽으면(Seq Scan) 행이 놓인 순서다. `ORDER BY seat_id … FOR UPDATE`는 정렬한 뒤에 잠그므로 계획과 상관없이 순서가 같다. 빼면 계획이 다른 두 요청이 교착에 빠진다(테스트).

**advisory lock과 SERIALIZABLE의 차이**

1. 1인 한도는 "지금 몇 석 쥐었나 세고, 한도 안이면 넣는다"이다. 두 창이 서로 다른 좌석을 담으면 고치는 좌석 행이 겹치지 않고, 새로 넣을 선점 행은 아직 없어서 좌석 행 잠금으로는 막을 수 없다. 둘 다 "지금 2석"을 보고 통과해 6석이 된다(테스트). 서로 다른 행을 쓰는데 서로가 읽은 것에 기대어 틀어지는 이 모양을 write skew라고 한다.
2. advisory lock은 앱이 정한 키에 거는 잠금이다. 표의 행과는 상관없다. 여기서는 키가 "사용자·회차"이고, 트랜잭션 단위(`pg_advisory_xact_lock`)라 커밋·롤백 때 저절로 풀린다. 같은 키의 요청끼리만 줄을 선다. 뒤 요청은 잠금을 받은 뒤 별도 문장에서 좌석 수를 센다. READ COMMITTED는 문장마다 스냅샷을 새로 잡으므로 앞 요청이 커밋한 선점이 보인다(REPEATABLE READ였다면 첫 문장 때의 스냅샷이라 보지 못한다). 미리 막는 방식(비관적)이다. 같은 자원을 다루는 코드가 모두 같은 키로 잠가야 한다는 약속이 필요하다.
3. SERIALIZABLE은 읽기를 막지 않는다. 누가 무엇을 읽고 썼는지 기록해 두었다가, 하나씩 차례로 실행했을 때와 다른 결과가 날 수 있는 조합을 40001로 실패시킨다. 읽은 것을 상대가 고친 관계(rw 의존)가 두 번 이어지면 고리가 될 수 있다고 보고 실패시키므로, 실제로는 문제가 없어도 실패할 수 있다. 같은 행에 쓰면 기다리는 것은 READ COMMITTED와 같다. 나중에 되돌리는 방식(낙관적)이다. 그래서 앱이 재시도해야 하고, 어느 쪽이 실패할지 정해져 있지 않다.
4. "무엇을 읽었나"를 기록할 때(술어 잠금), 인덱스로 찾은 범위는 그 인덱스 페이지 단위로 남는다. 그래서 실제로는 상관없는 요청도, 서로 읽고 쓴 범위가 같은 인덱스 페이지에 걸리면 실패할 수 있다. 같은 회차의 다른 사용자 둘이 다른 좌석을 담아도 대부분 한쪽이 되돌려졌다(측정).
5. 격리 수준은 트랜잭션 전체에 걸린다. 그래서 SERIALIZABLE을 쓰면 한도뿐 아니라 좌석 경쟁도 바뀐다. 같은 좌석을 기다린 쪽이 조건을 다시 보지 않고 40001을 받아 처음부터 다시 한다(테스트에서 재시도 1번). 좌석 경쟁은 인기 회차에서 가장 흔한 일이라, 진 요청마다 재시도가 한 번 더 든다.
6. 그래서 경쟁이 드문 한도는 좁은 키로 미리 줄을 세우고(advisory lock), 경쟁이 잦은 좌석은 READ COMMITTED의 조건부 UPDATE로 기다린 뒤 다시 보게 했다.

### 3단계 — 설명할 수 있어야 할 것

**멱등 키를 먼저 넣는 이유**

1. 같은 요청이 두 번 오는 일은 흔하다. 사용자가 버튼을 두 번 누르거나, 응답이 오기 전에 네트워크가 끊겨 화면이 다시 보내거나, 503을 받고 다시 보낸다. 주문 생성과 결제 요청은 두 번 처리되면 행이 하나 더 생긴다(결제는 돈이 두 번 빠진다).
2. 멱등 키는 "이 요청은 이미 처리했다(또는 처리 중이다)"를 DB에 남기는 행이다. 키는 `(사용자, 경로, 키)` 기본 키라 같은 키의 행은 하나뿐이다.
3. 업무보다 **먼저, 따로 커밋해** 넣는다(processing). READ COMMITTED에서는 커밋된 행만 보이므로, 커밋해 두어야 같은 키로 동시에 온 두 번째 요청이 이 행을 보고 409 `REQUEST_IN_PROGRESS`를 받는다. 업무 트랜잭션 안에 넣으면 두 번째 요청이 unique 인덱스에서 첫 요청이 끝날 때까지 연결을 쥐고 기다리고, 결제사 호출 같은 바깥 일도 트랜잭션 안에서 해야 한다.
4. 응답은 업무 트랜잭션 **안에서** 저장한다(done). 업무와 응답이 함께 커밋되거나 함께 사라지므로 "주문은 생겼는데 키는 처리 중"이 남지 않는다. 다시 보낸 요청은 저장한 응답을 그대로 받는다(`Idempotent-Replayed`).
5. 처리 중에 서버가 죽으면 키가 processing으로 남는다. 1분이 지나면 다음 요청이 넘겨받는다. 이때 `owner_token`을 새것으로 바꾸고, 저장·삭제는 내 `owner_token`일 때만 하므로, 늦게 살아난 옛 요청이 넘겨받은 요청의 응답을 덮지 못한다(saveInTx가 0행이면 업무까지 되돌린다).
6. 결제는 키만으로는 부족하다. 키 행은 5xx면 지워져 같은 키로 다시 보낼 수 있어야 하는데, 그 사이 결제사는 이미 결제를 만들었을 수 있다. 그래서 결제 행을 결제사를 부르기 전에 커밋하고(결제 id가 결제사 쪽 멱등 키), 결제 요청은 같은 키로 만든 결제를 먼저 찾는다. 다시 보낸 요청이든 넘겨받은 요청이든 결제 행이 하나이고, 결제사도 같은 id로 같은 결제를 돌려준다.

**SKIP LOCKED는 무엇을 건너뛰나**

1. `SELECT … FOR UPDATE SKIP LOCKED`는 고른 행 중 다른 트랜잭션이 잠근 행을 기다리지 않고 결과에서 뺀다. 잠그지 않은 행만 잠가서 돌려준다.
2. 정리 작업 1(좌석 풀기)과 2(주문 취소)가 쓴다. 지금 그 좌석이나 주문을 쥔 트랜잭션은 결제 확정, 취소, 선점(만료된 좌석 다시 잡기)이다. 정리가 그 행을 기다리면, 사용자 요청이 끝날 때까지 정리 한 바퀴가 멈추고, 그동안 다른 만료 행도 풀리지 않는다.
3. 건너뛴 행은 다음 바퀴(10초 뒤)에 다시 본다. 그때는 확정이 sold로 바꿨거나(대상 아님), 만료를 보고 환불로 갔거나(좌석은 held로 남아 이번에 풀린다), 다른 사람이 다시 선점했다(만료 전이라 대상 아님). 어느 쪽이든 두 번 팔리지 않는다(C3, 테스트).
4. 건너뛴 행은 `LIMIT 500`에 세지 않는다. 잠금(LockRows)이 Limit 아래에서 일어나기 때문이다(리뷰에서 실행 계획으로 확인).
5. 정리는 기다리지 않으므로 교착의 고리에 들 수 없다. 다른 요청이 정리를 기다리는 것도 정리가 그 행을 쥔 짧은 시간뿐이다.
6. 환불·대사(3·4단계)는 SKIP LOCKED가 아니라 아예 잠그지 않고 고른다. 결제사를 부르는 동안 결제 행을 쥐면, 그 결제의 웹훅 확정(주문 → … → 결제)과 반대 순서가 되어 교착한다(실험 E5). 반영은 새 트랜잭션에서 웹훅과 같은 순서(주문 먼저)로 하고, `requested`일 때만 바꾼다.

**웹훅 순서가 뒤바뀌면 어떻게 되나**

1. 결제사는 같은 결제의 이벤트를 여러 번(재전송), 순서를 바꿔, 결제 요청의 응답보다 먼저 보낼 수 있다. 우리는 이벤트가 온 순서가 아니라 **결제 행의 지금 상태**로 판단한다.
2. 이벤트 id는 `payment_webhooks`의 기본 키다. 같은 이벤트가 다시 오면 `INSERT … ON CONFLICT DO NOTHING`이 0행이라 duplicate로 200만 준다. 동시에 두 번 오면 두 번째가 unique 인덱스에서 첫 번째가 끝나길 기다린 뒤 0행을 받는다(테스트).
3. 결과가 중간 상태보다 먼저 오면(out_of_order): 결과(succeeded)로 확정하고, 뒤에 온 중간 상태(processing)는 ignored다. 중간 상태는 주문을 잠그지도 않는다.
4. 웹훅이 결제 요청의 응답보다 먼저 오면(early): 결제 행은 결제사를 부르기 전에 커밋했으므로 이미 있다. 확정하고 `provider_ref`도 웹훅이 채운다. 결제 요청의 마지막 트랜잭션은 `provider_ref IS NULL`일 때만 채우므로 덮지 않고, 202에 지금 상태(succeeded)를 준다.
5. 성공과 실패가 엇갈리면: failed로 정한 결제에 성공이 늦게 오면(대사가 먼저 failed로 정함) 돈을 받았으니 refund_pending으로 보낸다. 성공한 결제에 실패가 오면 결제사가 끝 상태를 바꾸지 않는다는 약속을 어긴 것이라 unmatched로 남기고 경보를 낸다.
6. 웹훅이 끝내 오지 않으면(lost): 30초 넘은 requested를 대사가 결제사에 다시 묻는다. 결제사가 모르면 그 id를 무효로 해 둔 뒤 failed로 바꾼다. 무효로 해 두지 않으면 넘겨받은 요청이 그 뒤에 같은 id로 결제를 만들어 돈만 받고 결제는 failed로 남는다.
7. 처리 중에 실패하면(잠금 대기 시간 초과 등) 웹훅 행도 함께 되돌려진다. 결제사가 2xx를 받을 때까지 다시 보내므로 다음 번에 처리된다. inbox 행을 처리보다 먼저 따로 커밋하면 이 재전송이 duplicate로 버려진다(변이 시험).

리뷰에서 나와 고친 것(PR 설명):
- 설계: 화면과 API를 같은 origin에 두어 CORS를 켜지 않는다. Secure 쿠키는 `__Host-` 이름. 속도 제한·argon2 동시 2개를 미루지 않고 넣었다. 훅은 루트가 아니라 보호 범위에(없는 경로가 403이 되지 않게).
- 인증 경로: IP+이메일만 세면 한 IP가 이메일을 바꿔 보내 카운터(LRU 5,000개)를 밀어낼 수 있었다 → 로그인은 IP 하나로도 센다(분당 100회). 프록시 뒤 IP 설정(`TRUST_PROXY`, `true`·숫자 거절). 401·403·429에도 `no-store`. 저장된 해시가 깨져 있으면 500 대신 같은 401.
- 관리자: 로그인 응답의 역할이 세션과 어긋날 수 있었다 → 세션을 만들 때 읽은 역할을 응답에 쓴다. 명령이 가입 시각을 보여 준다(이메일 확인이 없어서). 판매 현황에 회차 정보, 환불 실패 목록에 결제사 번호·주문 상태·회차, 다시 시도 응답에 `changed`.
- 회차 등록: 작품을 `{ id }`와 `{ title }` 중 하나로 받으면서 모르는 키를 버려, 폼의 select 값(문자열 id)과 제목이 함께 오면 새 작품이 생겼다 → 둘 다 오면 400. 0년 근처 시각이 500이었다 → 2000~2099년. 회차·작품은 지울 수 없어서 지난 판매 종료와 같은 제목을 422로 막는다. 먼저 넣은 같은 회차를 기다리는 경로를 다른 연결로 고정했다. 큰 공연장(1만 3천 석 넘게)은 한 문장 파라미터 한도에 걸려 나눠 넣는다.

로컬과 CI에서 부딪힌 것:
- GitGuardian이 테스트의 비밀번호 같은 글자(`normalizePassword("…")`)를 Generic Password로 잡았다. 테스트 값은 코드에서 만들어 쓰고, 이미 올린 브랜치는 한 커밋으로 합쳐 `--force-with-lease`로 다시 올렸다.
- `.github/workflows`를 바꾼 push는 토큰에 workflow 권한이 있어야 해서 `gh` 자격 증명으로 올렸다.
- `make_interval(secs => CASE …)`는 파라미터 형식을 정하지 못해 42883이다 → `::int`.
- 세션 수 제한이 한 트랜잭션에서 만든(만든 시각이 같은) 세션을 11개 남겼다 → 방금 만든 것과 나머지 9개를 남긴다.
- 테스트 DB를 지울 때 autovacuum이 붙어 있으면 `DROP … WITH (FORCE)`가 42501로 실패해 DB가 남았다 → 잠시 뒤 다시 시도한다.
- `@fastify/rate-limit`은 한 요청에 경로 설정의 제한 하나만 돈다(같은 요청에 두 번째 `rateLimit` 훅은 건너뛴다). IP 하나 제한을 더하려고 세 제한을 모두 `createRateLimit` + `preHandler`로 바꾸고 429를 한 곳에서 보낸다.
- Fastify 5는 `trustProxy`에 숫자(앞단 프록시 수)를 주면 아무 프록시도 믿지 않는다(바로 붙은 쪽을 확인할 수 없어서). 그래서 `TRUST_PROXY`는 주소·CIDR만 받는다.
- `app.inject`는 늘 127.0.0.1에서 오므로 속도 제한 테스트끼리 카운터가 섞인다 → 테스트마다 `remoteAddress`를 다르게.

미룬 것:
- 속도 제한 저장소는 메모리라 서버마다 따로 센다. 여러 서버가 같이 세는 저장소(Redis 등)와 앞단 제한(WAF)은 배포할 때 정한다(10장 61).
- 가짜 해시는 처음 쓸 때 만든다. 프로세스마다 첫 실패 로그인 한 번이 두 배 걸린다.
- 이메일 확인, 비밀번호 바꾸기, 전체 로그아웃은 없다(생기면 그 사용자의 다른 세션을 모두 지운다).
- 회차 시각 수정·삭제와 공연장 등록은 없다. 같은 새 제목으로 동시에 등록하면 같은 제목의 작품이 둘 생길 수 있다(10장 66).
- 판매 현황은 `holds`를 회차로 찾을 인덱스가 없어 순차 탐색이다. 환불 실패 목록은 100개와 `hasMore`뿐이다(10장 65, 6단계).
- 개발 DB에는 `npm run db:migrate -w @seat-booking/api`를 돌려야 한다(지금 0001까지 적용돼 있어 0002~0006이 한꺼번에 들어간다). 5단계 화면 전에 `.env`에 `APP_ORIGIN`·`COOKIE_SECURE=false`를 넣는다(`.env.example`).

### 4단계 — 설명할 수 있어야 할 것

**세션과 JWT의 장단점**

1. 세션은 서버가 상태를 갖는다. 쿠키에는 뜻 없는 무작위 토큰만 있고, 요청마다 서버가 DB에서 그 토큰의 사용자를 찾는다. JWT는 사용자 id·역할·만료를 담고 서버가 서명한 토큰이다. 서버는 서명만 확인하고 DB를 보지 않는다.
2. JWT의 장점은 DB를 보지 않는다는 것이다. 여러 서비스가 중앙 저장소 없이 같은 토큰을 확인할 수 있다.
3. JWT의 단점은 그 장점의 뒷면이다. 서버가 상태를 갖지 않으니 만료 전에 끊을 수 없다. 로그아웃·역할 변경·도난이 만료까지 남는다. 그래서 만료를 짧게 하고 refresh 토큰과 차단 목록을 두는데, 그러면 다시 서버 상태가 생긴다. 토큰에 담은 역할은 바꿔도 만료까지 옛 값이다. 서명 키 관리와 알고리즘 실수(`alg: none`, HS/RS 혼동)도 따라온다.
4. 세션의 단점은 요청마다 DB를 한 번 본다는 것과, 만료된 행을 지워야 한다는 것이다. 여기서는 세션 조회가 원래 하던 사용자 확인 SELECT를 대신하므로 왕복 수가 같고(기본 키 조인), 만료 행은 정리 작업 6이 500행씩 지운다.
5. 이 프로젝트는 앱 하나와 DB 하나이고, "로그아웃·역할 변경을 바로 끊는다"가 필요했다. 그래서 세션을 골랐다(10장 55). 테스트가 이것을 확인한다. 로그아웃하면 그 쿠키는 401, 관리자에서 내리면 다음 요청부터 403, 올리면 그 사용자의 세션을 모두 지운다.
6. 세션 토큰은 DB에 SHA-256만 둔다. DB가 새도 그 값으로 쿠키를 만들 수 없다. 토큰이 무작위 256비트라 느린 해시가 필요 없다(비밀번호와 다르다).

**SameSite=Lax가 막는 것과 못 막는 것**

1. SameSite는 다른 사이트에서 시작한 요청에 브라우저가 쿠키를 붙일지 정한다. 여기서 사이트는 origin이 아니라 등록 가능한 도메인(eTLD+1)과 scheme이다. `a.example.com`과 `b.example.com`, 같은 호스트의 다른 포트는 origin은 다르지만 같은 사이트다.
2. Lax가 막는 것: 다른 사이트에서 보낸 POST 폼, `fetch`·XHR, 이미지·iframe 같은 하위 요청에는 쿠키를 붙이지 않는다. 그래서 고전적인 CSRF(공격 사이트가 우리 API로 폼을 자동 제출)는 쿠키 없이 와서 401이다.
3. 못 막는 것 하나: 다른 사이트에서 링크를 눌러 오는 최상위 GET에는 쿠키가 붙는다. GET으로 상태를 바꾸는 경로가 있으면 뚫린다. 그래서 상태를 바꾸는 일은 POST로만 하고, CSRF 확인도 POST·PUT·PATCH·DELETE에 건다.
4. 못 막는 것 둘: 같은 사이트의 다른 origin(다른 서브도메인, 다른 포트)에서 오는 요청은 cross-site가 아니라 쿠키가 붙는다. 서브도메인 하나가 뚫리면 그곳에서 우리 API를 부를 수 있다. 그래서 Origin을 허용 목록과 정확히 맞춰 본다.
5. 못 막는 것 셋: 로그인 CSRF. 공격자가 자기 계정으로 로그인하는 폼을 피해자 브라우저에서 제출하게 하면, 피해자의 쿠키가 필요 없고 응답의 Set-Cookie가 최상위 탐색이라 받아들여진다. 피해자는 공격자 계정으로 결제·예매를 하게 된다. 그래서 로그인·가입·로그아웃에도 CSRF 확인을 건다(폼은 사용자 지정 헤더를 붙일 수 없다).
6. 못 막는 것 넷: SameSite를 모르는 오래된 브라우저, 그리고 우리 origin 안의 XSS. XSS는 같은 origin 요청이라 어떤 CSRF 방어도 소용없다. HttpOnly는 쿠키를 읽지 못하게 할 뿐 요청은 막지 못한다.
7. 그래서 Lax 위에 셋을 더 본다(10장 58): `Sec-Fetch-Site: cross-site` 거절, Origin 허용 목록(`null`도 거절), `X-Requested-With: seat-booking`. 다른 사이트의 폼은 헤더를 붙일 수 없고, 다른 origin의 `fetch`가 헤더를 붙이면 preflight가 먼저 나가는데 CORS를 켜지 않았으니 브라우저가 본 요청을 보내지 않는다.

### 5단계 — 설명할 수 있어야 할 것

**서버 상태와 화면 상태를 어떻게 나눴나**

1. 서버 상태는 서버만 바꿀 수 있는 사실이다. 좌석이 비었는지, 내 선점·주문·결제가 어떤 상태인지, 내가 누구인지. 이것은 TanStack Query 캐시에만 두고, 화면 컴포넌트의 state로 옮겨 적지 않는다(`["seatMap", id]`, `["myPerformance", id]`, `["order", id]`, `["orders"]`, `["me"]`, `["admin", …]`).
2. 화면 상태는 서버가 모르는 것이다. 고른 좌석, 고른 결제 상황, 멱등 키, 서버 시계와의 차이. 고른 좌석과 멱등 키는 새로고침·로그인을 오가도 남게 `sessionStorage`에 둔다.
3. 낙관적 갱신을 하지 않는다. 좌석은 그사이 다른 사람이 가져갈 수 있고, 결제는 웹훅이 와야 끝나기 때문이다. 바꾼 뒤에는 관련 키를 무효로 해 다시 읽는다(선점 → 좌석 지도·내 선점, 취소 → 주문·좌석 지도·내 선점·내 예매).
4. 서버가 혼자 바꾸는 것(결제 확정, 선점 만료)은 화면이 알 길이 없어서, 주문 화면이 응답으로 다시 읽기 간격을 정한다. 결제 확인 중이면 1초(15초 뒤 5초), 결제 마감 뒤면 2초, 끝나면 멈춘다. 폴링이 상태 변화를 보면 그 회차의 좌석 지도와 내 예매를 무효로 한다.
5. 고른 좌석은 서버 상태가 바뀔 때마다 맞춘다. 좌석 지도를 다시 읽을 때 그사이 선점·판매된 좌석을 고른 목록에서 빼고 알린다.
6. 누가 로그인했는지도 서버 상태다. 로그인·로그아웃·세션 만료·다른 탭에서 계정이 바뀌면 사용자별 캐시를 지운다(다른 사용자의 주문이 남아 보이지 않게).

**선점 시간이 끝나면 화면은 무엇을 하나**

1. 화면의 타이머는 서버 시계로 센다. 응답의 `serverTime`과 PC 시계의 차이를 왕복의 가운데로 재고, 왕복이 짧은 표본만 받는다. 다시 보낸 응답(`Idempotent-Replayed`)의 옛 시각은 버린다.
2. 타이머는 판단하지 않는다. 결제 마감(`payBy`, 선점 만료 30초 전)이 지나면 결제 버튼만 끈다. 그 30초는 결제 요청이 결제사를 부르고 돌아올 여유다.
3. 마감 뒤에는 주문을 2초마다 다시 읽는다. 서버는 선점이 지난 pending 주문을 정리 작업이 돌기 전이라도 cancelled(expired)로 준다. 화면은 그것을 받아 "시간이 초과되어 주문이 취소되었습니다"와 "좌석 다시 고르기"를 보인다.
4. 그때 결제가 확인 중(requested)이면 끝난 것이 아니다. 확정이 잠금을 기다리던 중이면 paid가 될 수 있고(C3), 결제됐는데 늦게 확정되면 환불로 간다. 화면은 "결제 결과 확인 중, 결제됐다면 자동 환불"을 보이며 계속 읽는다.
5. 좌석 지도는 만료된 선점을 빈 좌석으로 보인다(서버가 그렇게 준다). 다른 사람은 정리 작업을 기다리지 않고 그 좌석을 고를 수 있다.
6. 화면이 PC 시계만 믿고 "만료"를 정하면, PC 시계가 빠를 때 아직 살아 있는 선점을 버리게 하고 느릴 때 마감 뒤에 결제를 누르게 한다. 그래서 만료는 서버의 대답으로만 보인다.

### 6단계 — 설명할 수 있어야 할 것

**무엇이 병목이었고 어떻게 찾았나**

1. 처음 예상은 DB였다(설계 1장의 이력서 주장도 "인덱스와 쿼리를 고쳐"였다). 그래서 재기 전에 설계 리뷰가 좌석 지도 한 번을 미리 쟀다. Node CPU 약 5ms, DB 실행 약 1.5ms로 Node가 먼저 찰 것으로 보였다. DB 쪽 지표만으로는 원인에 이름을 붙일 수 없어 Node 지표를 더했다: 이벤트 루프 사용률·지연, 연결을 기다린 시간, 경로별 서버 처리 시간.
2. 좌석 지도만 도착률을 단계로 올렸다(S2). 이벤트 루프 사용률은 도착률에 비례해 오르다(요청당 약 4ms) 초당 250건에서 1이 됐다. 그 뒤로 지연은 1.5초대로 뛰고 처리량은 240건에서 멈췄다.
3. 그때 DB를 보면 원인이 갈린다. 연결 10개 중 9.6개가 ClientRead로 쉬는데, 풀에서 연결을 기다리는 요청은 400개가 넘었다. DB가 Node를 기다리는 것이다. 이벤트 루프가 밀려 결과를 처리하고 연결을 돌려주는 것이 늦어진다. 연결 대기가 길어 보여도 풀이 원인이 아니다.
4. CPU 프로파일로 Node 시간이 어디에 쓰이는지 봤다(일한 시간 중). Drizzle이 행을 객체로 바꾸는 데 23%, pg 프로토콜 파싱·문자열 디코딩 29%, zod 응답 검증 12%, JSON 직렬화 8%였다. 2,000행을 객체로 받아 다시 JSON으로 만드는 일이 대부분이다. 질의는 이미 기본 키 범위 탐색이라 인덱스로 줄일 것이 없었다.
5. 한 번에 하나만 바꿨다. 좌석 지도 JSON을 PostgreSQL이 만들고(`json_agg`), Node는 그 글자를 그대로 보낸다. 같은 PC에서 개선 전과 후를 다섯 번씩 번갈아 돌려, 범위가 겹치지 않을 때만 나아졌다고 썼다.
   - 꺾이는 곳 근처(초당 225건)의 p95는 14.4 → 6.0ms였다.
   - 꺾이는 점은 250 → 약 1,000건이었다.
   - 미리 정한 C7(낮은 부하의 지도 p95)은 범위가 겹쳐 나아졌다고 쓰지 않았다. 그 부하에서는 Node에 여유가 있어 지도 지연을 고정 비용이 정한다.
6. 일이 사라진 것은 아니다. 요청 하나에 Node 3.9 → 1.1ms, postgres 2.0 → 3.5ms(합 5.9 → 4.6ms)다. API 하나와 DB 하나인 이 구성에서는 한 스레드인 Node를 덜고 여러 코어를 쓰는 DB로 옮기는 것이 맞다. API를 여러 대로 늘리면 DB CPU가 귀해지므로 Node에서 매핑·검증·직렬화를 덜어 내는 쪽이 맞다.

**연결 풀 크기는 어떻게 정했나**

1. 풀 크기는 처리량을 올려 보며 정했다. 지속 부하(S3: 선점 → 주문 → 결제)를 풀 5·10·20·40에서 단계로 올렸다(초당 120·160·200·240반복). 기준(쓰기 경로 p95 300ms 미만, 예상하지 않은 오류 0, 버린 반복 0)을 지키는 가장 큰 도착률을 견줬다.
2. 넷 모두 200까지 지키고 240에서 무너졌다. 무너진 이유는 풀이 아니라 Node였다(이벤트 루프 사용률 1). DB에서 실제로 일하는 연결은 풀 크기와 상관없이 평균 1.3~1.7개였다. 풀을 키우면 트랜잭션을 연 채 Node를 기다리는 연결만 늘었다(200에서 풀 5는 1.8개, 40은 6.8개).
3. 미리 정한 규칙("최대 도착률이 가장 좋은 값의 95% 안인 가장 작은 풀")은 5를 고른다. 확인 회차로 풀 5와 10을 다섯 번씩 번갈아 돌렸다. 풀 5가 다섯 쌍 모두 빨랐지만(p95 가운데 21 대 51ms) 범위가 38ms에서 맞닿아 "나아졌다"고 쓰지 않았다. 이 PC는 다른 프로세스 때문에 회차 사이 잡음이 크다.
4. 좌석 지도를 고친 뒤 다시 봤다. 지도의 일이 DB로 옮겨 가 S2 초당 1,000건에서 DB에 동시에 4개 넘게 들어간다. 풀 5는 활성 연결 4.4개에 줄이 생겼다(p95 11.5 → 24.5ms). 기준은 지키지만 여유가 없다.
5. 그래서 기본 풀은 10을 유지했다. 풀 크기는 "DB가 동시에 일할 수 있는 만큼"에 맞추는 것이고, 지금 그 수를 정하는 것은 Node 한 스레드다. 이 PC에서 Node가 포화할 때 DB의 동시 일은 S3에서 2개 안팎, 고친 S2에서 5개 안팎이었다. 10은 그보다 넉넉하고 PostgreSQL의 `max_connections` 100에도 한참 못 미친다.
